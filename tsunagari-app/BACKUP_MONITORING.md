# バックアップ・操作履歴・監視

管理者でログインし、プロフィール → **管理画面を開く → バックアップ・監視** を開きます。稼働監視とバックアップはNode.js版（`start-sns.cmd` / `server.mjs`）で利用できます。一般メンバーには管理画面を表示せず、APIでも管理者以外のアクセスを拒否します。

## 毎日のバックアップ

初期設定は **自動保存オン・7世代保存** です。サーバー起動の約5秒後と、その後1分ごとに保存時刻を確認し、前回の正常なバックアップから24時間経過していれば作成します。初回は起動後に作成します。PC停止中には動作せず、起動後に再開します。失敗した場合は1時間以上空けて再試行します。

「今すぐバックアップ」で手動実行できます。自動保存のオン・オフ、保存する世代数（7・14・30）は画面で変更できます。世代数には手動保存も含みます。古い世代は、新しいバックアップが検証まで成功してから整理します。保存履歴は最新30件を表示します。

保存するもの：

- SQLiteの整合したスナップショット（アカウント、投稿、返信、予定、設定、操作履歴など）
- DBから参照されている投稿の画像・動画、プロフィール画像（非表示の投稿も含む）
- 通知用の秘密鍵 `push-keys.json`（存在する場合）
- 各ファイルのサイズ・SHA-256を記録した `manifest.json`

SQLiteのWALを含む現在の確定データを `VACUUM INTO` で保存します。DBと参照先の添付をコピーして、DBの整合性・外部キー・ファイルのチェックサムを検証した後で保存済みにします。添付が見つからない、容量不足、権限不足などの場合は失敗として記録します。作成中のフォルダーは復元に使わないでください。

データの整合性を保つため、コピー中はNode.jsの処理が一時的に止まります。画像・動画が増えると時間がかかるので、大容量運用では専用のバックアップ処理への移行が必要です。

### 保存先

通常はデータフォルダーの隣です。たとえば `data-external-trial` を使っていれば `data-external-trial-backups` になります。管理画面に実際の保存先を表示します。

同じPC・同じディスク内のコピーは、PC故障やディスク故障への備えにはなりません。別ドライブなどを指定する場合、PowerShellで次のように起動します。

```powershell
$env:BACKUP_DIRECTORY = 'D:\TsunagariBackups'
.\start-sns.cmd
```

この指定はそのPowerShellで起動した場合に有効です。常時使う保存先はWindowsのユーザー環境変数 `BACKUP_DIRECTORY` に登録し、再サインイン後に起動してください。データフォルダーと同じ場所、その中、その親は指定できません。保存先を変更しても古い保存先のバックアップは自動移動しません。

バックアップは暗号化していません。アカウントのパスワードハッシュや通知の秘密鍵を含むため、管理者だけが読めるフォルダーに保管してください。Windowsのフォルダー権限は運用担当者が設定してください。GitHubにはデータ・バックアップ・鍵をアップロードしません。

## 復元

復元処理は **存在しない新しいフォルダー** にのみ書き込みます。現在のデータには上書きしません。壊れたバックアップや、添付が不足したバックアップは検証で拒否します。

1. SNSを `Ctrl+C` で停止します。
2. 管理画面で確認した保存先から、復元する `backup-...` フォルダーを選びます。
3. アプリの `tsunagari-app` フォルダーで、次のコマンドを実行します。`backup-実際の世代名` は選んだフォルダー名に置き換えてください。

```powershell
node restore-backup.mjs "C:\保存先\backup-実際の世代名" ".\data-restored"
```

4. 「復元完了」と表示されたことを確認します。`RESTORE_FAILED.txt` がある場合は未完了なので起動せず、原因を解消して別の新しいフォルダーへやり直してください。
5. 元の `data-external-trial` を別名（例：`data-before-restore`）に変更して残し、`data-restored` を `data-external-trial` に変更します。保存先をカスタマイズしている場合は、その起動設定に合わせて切り替えます。
6. `.sns-private` の固定URL設定はそのまま残し、`start-sns.cmd` で再起動します。
7. アカウント・投稿・画像・動画・予定を確認します。

復元後は全員が再ログインしてください。通知の登録と、未使用の招待コードは無効化します。各端末で通知をオンにし直し、招待コードは管理者が再発行してください。アカウントのID・パスワードはバックアップ時点のものです。バックアップ後の投稿・パスワード変更・利用停止などは含まれないため、必要に応じて再設定してください。

ソースコード・`.sns-private`（固定URL・トークン設定）はバックアップ対象外です。別PCへ移行する場合、同じ版以降のコードとNode.jsを用意し、固定URLを設定してください。

## 操作履歴

ログイン成功・失敗、ログアウト、登録、パスワード変更、招待発行、メンバー管理、投稿・返信、いいね、プロフィール、予定、固定コメント、通報、投稿管理、バックアップ操作・設定変更を記録します。履歴には操作者、操作種別、成功・失敗、HTTPステータス、日時を表示します。未認証の失敗は「未認証」として残します。

パスワード、Cookie、招待コード、認証トークン、投稿本文、リクエスト本文・検索語は記録しません。一般の操作履歴は対象APIの種類を記録します。投稿管理の対象ID・詳細な理由は従来の「投稿管理 → 操作履歴」で確認できます。

一般の操作履歴は365日、最大10万件を保持し、古いものから整理します。システム記録は30日、最大1万件です。従来の投稿管理の操作履歴には、この自動整理を適用しません。DBに直接アクセスできる管理者に対する改ざん防止・外部保管には対応していません。

## 監視する内容

- 起動からの稼働時間、メモリ使用量、DB接続、データ・バックアップ保存先の空き容量
- 起動後のリクエスト数、5xxエラー数、処理に2秒以上かかった回数
- 直近15分のログイン失敗（10件以上で警告）
- バックアップの失敗、未作成、26時間超の未更新、保存先でのファイル不在
- 通知の送信待ち（5分超）、添付削除の待機、通知送信・自動削除の処理エラー
- 操作履歴の保存失敗

監視画面は表示中に約15秒ごとに更新します。入力操作中は自動更新を止めます。「更新」ボタンでも確認できます。失敗通知はこの管理画面とシステム記録に表示します。メール・Slackなどへの外部通知は行いません。

これは **サーバー内部の状態監視** です。PC自体の停止、停電、回線断、ngrok経由の外部からの接続可否は、このサーバーだけでは検知・通知できません。24時間の外形監視が必要な場合は、別の場所から監視するサービスを追加してください。DBの読取不能時には監視API自体がエラーになり、画面に接続・処理エラーを表示します。

## 更新方法

SNSを停止し、既存データを手動バックアップしてから、更新版の `tsunagari-app` 内を上書きします。`data-external-trial`、`.sns-private`、バックアップ保存先は残してください。起動時に `0008_operations.sql` を自動適用します。更新前からの投稿管理履歴はそのまま残ります。

自動テストで権限、認証情報の非記録、保存・復元、復元後のログイン、失敗時の旧世代維持、世代整理、破損・不正パスの拒否、監視の警告、画面の文字エスケープを検証しています。Windowsの実ドライブとスマホ実機では更新後に確認してください。
